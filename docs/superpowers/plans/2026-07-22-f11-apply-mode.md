# F11: Apply-Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Origin:** `docs/superpowers/specs/2026-07-22-apply-mode-design.md`. That design established apply-mode as a **repository-neutral landing path** for any registered transformation on any bound repo (registry 5-of-7 neutral; the two plugin/corpus transformations are opt-in `profile:claude-plugin` overlay entries that merely *use* the neutral machinery). This plan builds it.

**Goal:** Let a validated propose-mode proposal **land** — turn a recorded F6/F7/F8/F9 proposal into a pushed branch + an opened PR (Path A, repository files through a Nave pen) or a guarded `gh` write (Path B, GitHub objects), with a human/CI merge as the confirmation that advances F5/F8 bases. Apply changes *only what happens after every existing gate passes* — it never weakens the registered-transformation, expected-SHA, stale/dirty-preflight, `allow_scheduled`, or post-exec-validation gates that already stand in front of `pen_exec`.

**Non-goal (explicitly out of scope, deferred to v2 or a dependent phase):**
- **`allow` (unattended direct push)** and **scheduled auto-apply** — v1 apply is interactive / PR-gated; `allow` behind `allow_scheduled: true` + a workspace apply policy is v2.
- **Auto-merge** — landing is a *reviewed* merge; Pulse opens the PR, a human or CI merges it, and Pulse detects the merge. Pulse never merges.
- **F4 dependency-coherence apply** — the richest *neutral* apply use-case (fleet-wide dependency bump + lockfile landing) depends on the unbuilt **F4 dependency-coherence adapters**. `refresh-node-lockfile` / `regenerate-docs-index` give apply-mode its neutral proof today; fleet-wide coherence apply waits on F4.

**v1 boundary (settled 2026-07-22):** PR-first, human/CI merges, scheduled auto-apply and `allow` direct-push deferred. This closes the open decision in the design's § Design forks.

**Architecture:** Every gate F11 needs already exists and already fires — F11 changes the branch taken *after* they pass. `pen_orchestrator.execute` (`lib/pulse/scripts/pen_orchestrator.py`) today blocks any `mutation_policy != "propose"` at lines 312–321, before a single Nave call, and hardwires `nave_adapter.pen_exec(..., commit=False, push_changes=False)` (line 450); its terminal success state is always `proposed`. `nave_adapter.pen_exec` (line 455) **already accepts** `commit`/`push_changes`/`message`. So Path A is: replace the blanket block with a policy-gated commit/push + a PR open, keeping every preceding gate. Path B is: implement the reserved `allow-listed`/`allow` `gh` writes under `on_mutation` for GitHub objects. Confirmation and base advancement (F5/F8) run through the existing run ledger (`resolve_run.py`, `lib/patterns/run-ledger.md`) as a resumable *propose-PR → detect-merge → advance-base* loop, with merge detection registered as a `check-gate` `GATE_EVALUATORS` entry so it is deterministic and idempotent.

**Tech Stack:** Python 3.10+ PEP 723 scripts, PyYAML, pytest, `gh` CLI, git, `nave` CLI. No new library dependencies — F11 wires existing seams (`pen_exec` push args, `read_repo_head`/`read_repo_file`, the run ledger, `on_mutation`) into a landing path.

## What already exists (verified 2026-07-22, develop head)

- **The block point (Path A):** `pen_orchestrator.execute` returns `blocked` for any `mutation_policy != "propose"` **or** `request_push=True` before any Nave call (`pen_orchestrator.py:312–321`); the reserved `allow-listed`/`allow` semantics are documented but unimplemented (`lib/patterns/repository-mutations.md` § `mutation_policy` values, "Current implementation status"). The terminal success state is `proposed`; `pen_exec` is called `commit=False, push_changes=False` (`pen_orchestrator.py:450`).
- **The push plumbing already exists:** `nave_adapter.pen_exec(runner, pen_name, argv, only, commit, push_changes, message)` (`nave_adapter.py:455`) accepts commit/push args — the orchestrator simply never sets them.
- **The guards F11 must preserve, all firing before exec:** forbidden-push check, pen-create, selection/pen-repo match, stale/dirty preflight (`working_tree == "clean"`, `freshness == "fresh"`, `divergence == "up-to-date"`, fail-closed on partial), the expected-SHA guard via injected `read_repo_head` (fail-closed on missing reader *or* any uncovered repo), and post-exec `validation` via injected `read_repo_file`.
- **The injectable filesystem seams already on `execute`:** `read_repo_file: (repo, path) -> bytes` and `read_repo_head: (repo) -> str`. F11 must supply a **real pen-clone reader** for both (a caller with filesystem/git access to the pen's clones); today only tests inject them.
- **The transformation registry** (`templates/transformations.yaml.template`, 7 entries): neutral `format-python` (`allow_scheduled: true`), `regenerate-from-template` (calls installed `nave`), `refresh-node-lockfile` (`json_schema` validation), `regenerate-docs-index` (`allow_scheduled: true`); the B1 offender `plan-sync-doc-patch` (argv runs `apply_doc_patch.py` by a **plugin-repo-relative path** that won't resolve in a doc-repo pen); and the two opt-in overlay entries `regenerate-corpus-navigate-skill`, `marketplace-entry-update` (both `profile:claude-plugin`).
- **Validation kinds** `VALIDATION_KINDS = {"none", "json_schema"}` (`mutation_plan.py:27`); `Proposal` has no `bound_paths` field (`mutation_plan.py:273`). T2 adds both.
- **The run ledger:** `resolve_run.py` (`create/next/update/gate-result/check-gate/lease`), cross-repo runs committed under `{workspace_root}/.hiivmind/github/runs/`; `check-gate` computes gates deterministically from a validated result file via named `GATE_EVALUATORS` (e.g. F5's `binding_edges_current`), fail-closed. T4 registers a merge-detection evaluator here.
- **Result contract:** `validate_result.py` kind `repo-mutation` (Path A) and the object-side kinds (Path B) validate today's propose-mode envelopes; T6 adds the `applied`/`pr_opened` states and the PR-URL / merged-SHA fields.
- **The propose-only drivers F10 lands** (`marketplace_sync_run.py`, `plan_sync_run.py`, `generated_artifact_run.py`) are F11's upstream: they *emit* the proposals F11 *lands*. F11 assumes F10; it adds an apply step behind the propose step, never a second proposal path.

## Global Constraints

- **Apply is opt-in and gated, never default.** Propose remains the default `mutation_policy`; a proposal lands only with an explicit, validated `allow-listed` (v1) opt-in. Every pre-exec gate above stays in force and fails closed — apply-mode adds a branch *after* validation succeeds, it never removes a gate.
- **Landing is a reviewed merge.** v1 apply = push a per-proposal branch + open a PR (Path A) / a precondition-guarded `gh` write (Path B). Pulse never merges. Base/marker advancement keys off a **detected merge**, never a push.
- **No new decision logic in the executor.** Classification/merge/drift rules stay in the pure libraries; the orchestrator and the reconciliation loop only assemble inputs, enforce gates, and record outcomes built from the same `Proposal` that gated execution — nothing reconstructed after the fact.
- **Neutral-first, two-suite discipline** (the fleet-scope audit's mandate). Every apply task lands and asserts at least one **neutral transformation on a non-plugin fixture repo** (`refresh-node-lockfile` on a Node repo / `regenerate-docs-index` on a docs repo); the two overlay transformations are demonstrated **separately**. Coverage distinguishes "not applicable" from "not tested".
- **Per-ecosystem tool absence is `blocked`, not assumed-present.** A neutral transformation whose toolchain (a Python formatter, `npm`, a docs generator) is absent in the pen fails closed as `blocked`, per ecosystem — apply-mode does not assume a single applier.
- **Resumable and partial-failure-safe.** The doc-pen path (A) and the GitHub-object path (B) fail independently; `finalize` advances only confirmed values; a run resumes from the ledger with idempotent, lease-guarded steps.
- **Every apply run writes a validated result on every exit** (including early `blocked`/ABORT) and self-validates via `validate_result.py`; a non-zero validator exit is a bug.
- `uv run pytest -q` and `git diff --check` pass before each task closes.

## Phase gate — after F11

- A validated `allow-listed` proposal for a **neutral** transformation on a non-plugin repo lands as a pushed branch + an opened PR; on a **detected merge** (never a push), the F5/F8 base advances off the merged SHA; the result validates with `applied`/`pr_opened` + PR URL + merged SHA.
- Every pre-exec gate (registered transformation, expected-SHA, stale/dirty preflight, `allow_scheduled`, bound-path `paths_changed`, post-exec validation) still fires and still fails closed; no push happens on a failed gate.
- `pen_orchestrator.execute` gains its first pushing caller **only** under `allow-listed` with a real pen-clone reader; `allow` (direct push) and scheduled auto-apply stay blocked/deferred.
- Path A (pen) and Path B (`gh` object) fail independently and resume from the ledger idempotently.
- The neutral apply path carries no plugin/overlay strings; the overlay transformations land through the **same** neutral machinery as a separate dogfood suite (two-suite discipline intact).

## Explicitly deferred (still gated on separate design)

- **`allow` (unattended direct push) + scheduled auto-apply** — v2, behind an explicit workspace apply policy + `allow_scheduled: true`; the confirmation model changes (no PR review gate), so it is its own scope.
- **Auto-merge** — out of scope by design; landing is always a reviewed merge.
- **F4 dependency-coherence apply** — fleet-wide dependency-bump + lockfile landing depends on the unbuilt F4 dependency-coherence adapters; `refresh-node-lockfile` / `regenerate-docs-index` prove neutral apply today, fleet-wide coherence apply waits on F4.
