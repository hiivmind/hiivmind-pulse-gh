# F11: Apply-Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Origin:** `docs/superpowers/specs/2026-07-22-apply-mode-design.md`. That design established apply-mode as a **repository-neutral landing path** for any registered transformation on any bound repo (registry 5-of-7 neutral; the two plugin/corpus transformations are opt-in `profile:claude-plugin` overlay entries that merely *use* the neutral machinery). This plan builds it.
>
> **Revised 2026-07-29** after an adversarial design review (GLM 5.2, report `.sdd-dispatch/delegate/001-review.md`). Three false/unsupported seam claims and a circular gate were found in the first draft and are corrected here: (C1) `pen_exec` has **no branch argument** — pushing today would push the pen's *current* (base) branch, so per-proposal branch creation is greenfield, not plumbing; (C2) Nave exposes **no pen-clone path**, so the "real reader" is a discovery contract that must be designed, not a file to drop in; (C3) `marketplace-entry-update` points at an **absent** `apply_marketplace_entry.py` and the old T1 PATH check (argv[0] only) passed it trivially; (I1) the merge gate must read a validated result file that only a merge-detection step can write, so the result-kind work is pulled ahead of the reconcile loop. Task count grew 6 → 8 to give the greenfield pen substrate (branch + clone discovery) and the result contract their own tasks.

**Goal:** Let a validated propose-mode proposal **land** — turn a recorded F6/F7/F8/F9 proposal into a pushed branch + an opened PR (Path A, repository files through a Nave pen) or a guarded `gh` write (Path B, GitHub objects), with a human/CI merge as the confirmation that advances F5/F8 bases. Apply changes *only what happens after every existing gate passes* — it never weakens the registered-transformation, expected-SHA, stale/dirty-preflight, `allow_scheduled`, or post-exec-validation gates that already stand in front of `pen_exec`.

**Non-goal (explicitly out of scope, deferred to v2 or a dependent phase):**
- **`allow` (unattended direct push)** and **scheduled auto-apply** — v1 apply is interactive / PR-gated; `allow` behind `allow_scheduled: true` + a workspace apply policy is v2.
- **Auto-merge** — landing is a *reviewed* merge; Pulse opens the PR, a human or CI merges it, and Pulse detects the merge. Pulse never merges.
- **F4 dependency-coherence apply** — the richest *neutral* apply use-case (fleet-wide dependency bump + lockfile landing) depends on the unbuilt **F4 dependency-coherence adapters**. `refresh-node-lockfile` / `regenerate-docs-index` give apply-mode its neutral proof today; fleet-wide coherence apply waits on F4.

**v1 boundary (settled 2026-07-22):** PR-first, human/CI merges, scheduled auto-apply and `allow` direct-push deferred. This closes the open decision in the design's § Design forks.

**Architecture:** Most gates F11 needs already exist and already fire — F11 changes the branch taken *after* they pass. `pen_orchestrator.execute` (`lib/pulse/scripts/pen_orchestrator.py`) today blocks any `mutation_policy != "propose"` at lines 312–321, before a single Nave call, and hardwires `nave_adapter.pen_exec(..., commit=False, push_changes=False)` (line 450); its terminal success state is always `proposed`. `nave_adapter.pen_exec` (line 455) **already accepts** `commit`/`push_changes`/`message` — the *push* half of Path A is a kwargs change. But two pieces the first draft assumed were plumbing are **greenfield** and must be built before the push flip is safe:
1. **Branch targeting (C1).** `pen_exec` and `pen_create` carry **no branch argument** (`nave_adapter.py:455–462`, `:425–430`); `--push-changes` pushes whatever branch each pen clone sits on — a freshly-created pen is on the **base branch**. Pushing today would push straight to `main`, breaching the PR-first boundary. The per-proposal branch `pulse/apply/{proposal_id}` — the whole PR-first mechanism — has to be *created and checked out per clone* before exec. That is new adapter surface (T3).
2. **Clone-path discovery (C2).** The `read_repo_head`/`read_repo_file`/pen-diff seams need a caller with filesystem access to the pen's clones, but **no Nave surface exposes a clone path** (`pen_orchestrator.py:43–49`, `:60–69` say so explicitly: `pen show`/`pen status` carry none, `nave materialize` fetches from the API not the working tree). Today only tests inject these readers. A real reader needs a *defined clone-root source* (a `nave` surface that prints clone roots, or a documented out-of-band source), fail-closed when absent (T3).

So Path A is: **T3** build the pen substrate (per-proposal branch + a real clone reader with a defined path source), **T4** replace the blanket block with a policy-gated commit/push onto that branch keeping every preceding gate, **T5** give landings a result kind, **T6** open the PR and advance F5/F8 bases on a *detected merge* via a `check-gate` evaluator that reads T5's validated result file. Path B (**T7**) implements the reserved `allow-listed`/`allow` `gh` writes under `on_mutation` for GitHub objects, with an explicit precondition object. **T8** proves it neutral end-to-end. Confirmation and base advancement run through the existing run ledger (`resolve_run.py`, `lib/patterns/run-ledger.md`) as a resumable *propose-PR → detect-merge → advance-base* loop.

**Tech Stack:** Python 3.10+ PEP 723 scripts, PyYAML, pytest, `gh` CLI, git, `nave` CLI. No new library dependencies — F11 wires existing seams (`pen_exec` push args, `read_repo_head`/`read_repo_file`, the run ledger, `on_mutation`) into a landing path and adds the branch-targeting + clone-discovery surface those seams turned out to lack.

- **The propose-only drivers F10 lands** (`marketplace_sync_run.py`, `plan_sync_run.py`, `generated_artifact_run.py`) are F11's upstream: they *emit* the proposals F11 *lands*. F11 assumes F10; it adds an apply step behind the propose step, never a second proposal path.

## Global Constraints

- **Apply is opt-in and gated, never default.** Propose remains the default `mutation_policy`; a proposal lands only with an explicit, validated `allow-listed` (v1) opt-in. Every pre-exec gate above stays in force and fails closed — apply-mode adds a branch *after* validation succeeds, it never removes a gate.
- **Landing is a reviewed merge.** v1 apply = push a per-proposal branch + open a PR (Path A) / a precondition-guarded `gh` write (Path B). Pulse never merges. Base/marker advancement keys off a **detected merge**, never a push.
- **A push never targets a base branch.** Every Path A push goes to `pulse/apply/{proposal_id}`, created and checked out per clone before exec; if the branch cannot be created/checked out on any selected repo, the run `blocked`s before any push (C1). This is the single largest blast-radius guarantee in F11.
- **No new decision logic in the executor.** Classification/merge/drift rules stay in the pure libraries; the orchestrator and the reconciliation loop only assemble inputs, enforce gates, and record outcomes built from the same `Proposal` that gated execution — nothing reconstructed after the fact.
- **Neutral-first, two-suite discipline** (the fleet-scope audit's mandate). Every apply task lands and asserts at least one **neutral transformation on a non-plugin fixture repo** (`refresh-node-lockfile` on a Node repo / `regenerate-docs-index` on a docs repo); the two overlay transformations are demonstrated **separately**. The new bound-path guard (T2) and the neutral acceptance (T8) must both exercise a neutral transformation — the security machinery may not be proven only on the overlay path (I7). Coverage distinguishes "not applicable" from "not tested".
- **Per-ecosystem tool absence is `blocked`, not assumed-present.** A neutral transformation whose toolchain (a Python formatter, `npm`, a docs generator) is absent in the pen fails closed as `blocked`, per ecosystem — apply-mode does not assume a single applier.
- **Resumable and partial-failure-safe.** The doc-pen path (A) and the GitHub-object path (B) fail independently; within Path A, partial cross-repo failure has a **defined** outcome (T4 — no half-pushed selection left unrecoverable); `finalize` advances only confirmed values; a run resumes from the ledger with idempotent, lease-guarded steps.
- **Every apply run writes a validated result on every exit** (including early `blocked`/ABORT) and self-validates via `validate_result.py`; a non-zero validator exit is a bug.
- `uv run pytest -q` and `git diff --check` pass before each task closes.

### Task 3: Pen apply substrate — per-proposal branch (C1) + real clone reader (C2)

**Files:**

**Interfaces:**

**Interfaces:**
- The blanket block at `pen_orchestrator.py:312–321` becomes policy-aware: `propose` still terminates at `proposed`; `allow-listed` (v1) proceeds — **after every existing gate passes and after T3 has put every clone on `pulse/apply/{proposal_id}`** — to `nave_adapter.pen_exec(..., push_changes=True, message=<attributed>)` (push implies commit; no redundant `commit=True`, M2), terminal state `pushed`. `allow` remains blocked in v1. `request_push=True` with `propose` is still a forbidden-push block. `request_push` is frozen to `False` under non-`propose` policies (M3).
- **Attribution message shape is declared** (M4): `message = "pulse-apply {proposal_id} by {gh_login}@{machine}"`, built from the `Proposal` — reproducible and greppable, never reconstructed.
- A real reader (`pen_clone_reader`, T3) satisfies `read_repo_head`, `read_repo_file`, and the T2 pen-diff from the pen's clones — so the guards that fail-closed-without-a-reader today actually run in apply mode.
- **Partial cross-repo failure (I4):** `nave_pen::ops::exec_pen` bails at the first failing repo and the orchestrator can only mark the whole selection `failed` (opaque stdout, `pen_orchestrator.py:71–84`). Under push that would strand commits on the early repos. Resolve it by **committing per repo but pushing only after every selected repo's exec + validation succeeds** (commit-all-then-push), so a mid-selection bail leaves *unpushed* local commits and a clean `failed` with no remote side effects; a retry re-runs the whole selection idempotently onto the same branch. (If a future Nave surface yields per-repo exec signal, single-repo-atomic push can be revisited — documented, not built now.)
- **SHA-staleness recovery (I2):** the base may advance between propose and apply (a human merge gate makes this likely). An expected-SHA mismatch is a **non-terminal `blocked-on-gate`** with a named, resumable recovery: rebuild `expected_shas` off current HEAD and re-run — not a dead terminal. The `Proposal` being frozen (`mutation_plan.py:273`) means recovery mints a **new** proposal from the refreshed SHAs; the plan states this explicitly so it is not discovered on day one.
- Fail-closed unchanged: stale/dirty preflight, expected-SHA mismatch (→ recoverable block), uncovered repo, and any post-exec validation failure all still `blocked`/`failed` **before** or **instead of** a push. A push never happens on a failed gate.

**Steps:**
- [ ] **Step 1: Write failing tests** — an `allow-listed` proposal on a clean/fresh pen with matching SHAs and satisfied `paths_changed` reaches `pushed` having driven `pen_exec(push_changes=True)` onto `pulse/apply/{id}` (never a base branch); a stale/dirty pen, an out-of-allowlist change, and a missing reader each block with no push; an SHA mismatch yields a **recoverable** `blocked-on-gate` (not terminal); a mid-selection exec failure leaves no pushed commits (partial-failure semantics); `allow` blocks (v1); `propose` still ends at `proposed`; **the existing `:147/:157` assertions are updated** to the new behavior. Neutral fixture (`refresh-node-lockfile` on a Node pen) is primary; overlay is a separate case.
- [ ] **Step 2: Implement** the policy-gated commit-all-then-push branch, the recovery block, and the attribution message; keep the propose path byte-for-byte unchanged.
- [ ] **Step 3: Update docs** — flip `repository-mutations.md`'s "Current implementation status" for `allow-listed`.
- [ ] **Step 4: Run full suite and commit** with `feat: land allow-listed pen apply as push`.
